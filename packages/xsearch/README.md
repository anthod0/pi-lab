# @pi-lab/xsearch [![NPM Version](https://img.shields.io/npm/v/@pi-lab/xsearch)](https://www.npmjs.com/package/@pi-lab/xsearch)

An `xsearch` tool for pi that answers a question with X permalinks as sources. It runs on one of two backends: xAI's `x_search`, or [twitterapi.io](https://twitterapi.io). Either way the result has the same shape.

The two are not priced alike. twitterapi.io bills **15 credits per returned post — $0.15 per 1,000** at its 100,000-credits-to-the-dollar rate, while xAI's `x_search` bills **$5 per 1,000 posts fetched** on top of model tokens. For the same posts that is roughly **33x cheaper**, which is the reason this backend exists.

> [@pi-lab/grok-build](../grok-build) is usually the better choice for reading X when the Grok Build CLI is installed and authenticated: it handles posts, threads and replies with more context. `xsearch` is for broader API-key searches, where you need more posts and many citation URLs.

## Backends

| Capability | xAI backend | twitterapi.io backend |
|---|---|---|
| Credential | `XAI_API_KEY` | `TWITTERAPI_IO_API_KEY` |
| Model setting | `model` | `synthesisModel` |
| Keyword post search | `x_keyword_search` | `advanced_search` |
| Account search | `x_user_search` | `mode: "users"` |
| Thread fetch | `x_thread_fetch` | `mode: "thread"` |
| Semantic search | `x_semantic_search` | not available |
| Post retrieval cost | $5 per 1,000 posts | $0.15 per 1,000 posts (15 credits each) |
| Account retrieval cost | $10 per 1,000 profiles | ~$0.94 per 1,000 accounts |
| Answer | generated by xAI, billed as model tokens | generated from the retrieved posts by `synthesisModel`, billed by that provider |
| Image understanding | forwarded when `enableImageUnderstanding` is set | attached when enabled and the model accepts image input |
| Video understanding | forwarded when `enableVideoUnderstanding` is set | poster frame when enabled, since chat models cannot ingest video |
| pi requirement | any supported version | a pi whose `ModelRegistry` provides `complete` — present in 0.99.2, absent in 0.80.6 |

The backend is chosen from your credentials: xAI when `XAI_API_KEY` is set, twitterapi.io otherwise. Set `backend` to pin one when both keys exist.

`model` and `synthesisModel` are separate keys because they mean different things. `model` is sent to xAI as-is; `synthesisModel` is looked up in pi's model catalogue. Keeping them apart means that adding an xAI key to an existing twitterapi.io setup cannot quietly send a pi model id to xAI — the twitterapi.io backend asks for `synthesisModel` instead of guessing.

**One call, or two.** The xAI backend does the whole job in one request: `x_search` finds the posts and xAI's model writes the answer from them. The twitterapi.io backend splits that in two: `xsearch` retrieves the posts, then a pi model you name in `synthesisModel` writes the answer from those posts alone. That second step is what this README calls **synthesis**, and it is why the two backends are billed differently.

## Install

```bash
pi install npm:@pi-lab/xsearch
```

## Usage

Export the key for the backend you want, then start pi:

```bash
export XAI_API_KEY=<your-api-key>          # or TWITTERAPI_IO_API_KEY
pi
```

`XAI_API_KEY` can also be provided through [@pi-lab/env](https://www.npmjs.com/package/@pi-lab/env).

Then ask in plain language:

```text
Search X for what people are saying about a topic you are tracking.
```

The answer comes from the model you configured, and `## Sources` lists the permalinks behind it. When the tool has something to disclose — a coverage gap, skipped media, a dropped link — it appends a `## Notes` section.

This is not a raw tweet API and does not guarantee original post objects.

## Settings

Configure under the `xsearch` key in pi settings. User settings live in `~/.pi/agent/settings.json`, project settings in `<cwd>/.pi/settings.json`, and project settings win.

```json
{
  "xsearch": {
    "model": "<xai-search-model-id>",
    "synthesisModel": "<provider>/<model>",
    "backend": "auto",
    "enableImageUnderstanding": false,
    "enableVideoUnderstanding": false,
    "maxMediaPerSearch": 4,
    "minRequestIntervalMs": 5000,
    "retryBaseDelayMs": 5000,
    "maxPages": 5,
    "maxPagesCeiling": 20
  }
}
```

Defaults:

- `model`: unset — the xAI search model id. Omit it to use the extension's built-in xAI search default. Never used for synthesis.
- `synthesisModel`: unset — required by the twitterapi.io backend. The pi model that writes the answer from the retrieved posts; a `provider/model` id resolved through pi's catalogue.
- `backend`: `auto` — one of `auto`, `xai`, `twitterapi`.
- `enableImageUnderstanding`: `false` — on the xAI backend this asks `x_search` for image understanding; on twitterapi.io it attaches post images to the synthesis request, for models that accept image input.
- `enableVideoUnderstanding`: `false` — the same for video on xAI; on twitterapi.io it attaches each video's poster frame, since chat models cannot ingest video, and says so in `## Notes`.
- `maxMediaPerSearch`: `4` — most media attachments per search on twitterapi.io. Values above 20 are capped; anything else that is not a non-negative integer falls back to the default.
- `minRequestIntervalMs`: `5000` — spacing between paged requests. twitterapi.io rate-limits per key, and a new unpaid account allows 0.2 QPS (one request every five seconds), so unpaced pagination can rate-limit itself. Set `0` to switch pacing off. Retries are spaced by `retryBaseDelayMs` instead, so lowering that can burst below the key's limit even with pacing on, and two searches running at once can still exceed it. Values above 600000 are capped; a negative or non-finite value falls back to the default.
- `retryBaseDelayMs`: `5000` — base delay for retry backoff, and the floor applied to a server-supplied `Retry-After`. Values above 600000 are capped; a negative or non-finite value falls back to the default.
- `maxPages`: `5` — base page budget per search, never above `maxPagesCeiling`. Values above 100 are capped; anything that is not a positive integer falls back to the default.
- `maxPagesCeiling`: `20` — hard ceiling for the adaptive page budget. Values above 100 are capped; anything that is not a positive integer falls back to the default.

## xAI backend

Set `model` to the xAI search model you want; a fast non-reasoning one is fine for most searches. Cost and availability live in the xAI docs:

- [xAI models](https://docs.x.ai/docs/models) — available models, pricing and tool costs.
- [xAI X Search](https://docs.x.ai/developers/tools/x-search) — supported `x_search` behaviour and parameters.

`x_search` takes the search type from your question, so it performs keyword, semantic, account and thread search natively. Handle filters and dates are forwarded to it once validated — at most 20 handles per filter, `YYYY-MM-DD` dates, and allowed and excluded handles cannot be combined — while `count` and `queryType` are not part of its request. A `mode: "thread"` request appends the thread permalink to the query, which is where its native search reads the reference from.

## twitterapi.io backend

Sign up at [twitterapi.io](https://twitterapi.io) — a free trial credit is included, and no X login or developer account is needed — then export the key before starting pi:

```bash
export TWITTERAPI_IO_API_KEY=<your-api-key>
pi
```

Set the synthesis model in pi settings:

```json
{
  "xsearch": {
    "synthesisModel": "<provider>/<model>"
  }
}
```

This backend needs a pi whose model registry exposes `complete`. Without it the tool fails immediately with a message naming the requirement, rather than a `TypeError`. The xAI backend is unaffected.

twitterapi.io returns raw posts rather than an answer, so `xsearch` retrieves them and asks `synthesisModel` to answer from those posts alone under a citation-constrained prompt. Citations are matched against the permalinks that were actually retrieved, and only x.com / twitter.com URLs can match by status id, so a look-alike URL on another domain is never accepted as a source. A link that matches nothing is dropped from `## Sources` and reported in `## Notes`. When the model cites nothing at all, `Sources` lists the posts the search retrieved, which matches how the xAI backend behaves.

### Date windows, and why some offsets paginate further

twitterapi.io resolves `since:` / `until:` at **04:00 UTC**, not midnight, so the upstream window rarely lines up with a local day. What that costs depends on your offset (`offset = local − UTC`):

| Offset | Effect | Cost |
|---|---|---|
| West of UTC−4 (e.g. UTC−6) | The upstream window ends before your day does, leaving a short uncovered tail. | Nothing extra. The tail is disclosed in `## Notes`. Older start-padding posts can still be discarded, and those never extend the budget. |
| UTC−4 | Aligned. | Nothing. |
| East of UTC−4 (e.g. UTC+2) | The upstream window runs past your day end, so the newest `4 + offset` hours fall outside it and are discarded. | Extra pages, at 15 credits per returned post, up to `maxPagesCeiling`. |

The discarded stretch is `4 + offset` hours: 6 hours at UTC+2, 14 at UTC+10.

Results arrive newest-first (`Latest`, the default; `Top` is ranked), so that out-of-window band comes before the posts you asked for. On a busy topic it can use up the whole base budget, so pages that cross the band are not charged against `maxPages`: the budget stays available to fill `count` once the scan reaches your window. Offsets without a band pay for every page.

Paging follows the upstream cursor rather than the page's contents, so an empty page does not end the walk while there are more pages and a cursor to follow. A search ends when the upstream runs out, when `count` is filled, when the budget is spent, or when the cursor repeats or is missing. A thread fetch has no `count` to fill, so it stops on any of those, and on an empty page as well. Total pages are capped by `maxPagesCeiling`, and whatever was skipped is reported in `## Notes`.

Retrieval cost is bounded by `maxPagesCeiling`: 20 pages of up to 20 posts each is roughly $0.06 at 15 credits per post. That covers retrieval only (see [Cost](#cost)), and retries are not counted. A truncated result always says so.

### Search modes

An optional `mode` selects what to search:

| `mode` | What it does | Extra parameters |
|---|---|---|
| `posts` (default) | Keyword search over posts. | `count` (default 10, max 50), `queryType`, `from_date`, `to_date`, handle filters |
| `users` | Finds X accounts by keyword, answered with profile URLs as sources. | `count` (default 20, max 50) |
| `thread` | Reads one post's thread context and answers from it. | `tweet` (a post id, or any X permalink in the thread) |

Handle filters take at most 20 handles each.

On this backend a mode refuses parameters it cannot use rather than ignoring them: handle filters, dates and `queryType` are refused for `users`, and those plus `count` for `thread`, because an account search cannot be filtered by account and one thread has no date range. `mode` and `tweet` are validated on both backends — `mode` must be one of the three, and `tweet` is required for `thread` and refused in any other mode — and so is the question itself, before any credentials are read, so an invalid call reports the real problem. On the twitterapi.io backend, thread mode passes your question to synthesis and identifies the thread in `## Notes`. Semantic search exists on xAI only.

Account search matches your keyword as a sub-string of names, handles and bios. There are no word boundaries and no ranking, so `coding` also matches `clcoding`, and a multi-word query can return nothing at all. When that happens, `## Notes` suggests a single keyword.

`X Search Calls` is reported the same way on both backends; on twitterapi.io it is a synthetic `0`/`1` marker for the synthesis pass, not a count of upstream requests.

### Cost

Retrieval is metered per returned item. Posts are **15 credits each**, which at twitterapi.io's 100,000-credits-to-the-dollar rate is **$0.15 per 1,000 posts** against xAI's **$5 per 1,000 posts fetched** — about **33x cheaper** for the same volume. A call that returns a single post or none at all is charged the 15-credit minimum.

Account search is the exception: a 20-account page measured **1,890 credits** (~$0.019), about **$0.94 per 1,000 accounts**. That still undercuts xAI's **$10 per 1,000 profiles**, but it is several times the per-post rate. A 5-post thread fetch is about **90 credits**.

Those figures cover retrieval — the posts. **Synthesis**, the step that turns retrieved posts into the answer you read, is a separate charge. On this backend it is your own `synthesisModel` writing the answer, and that model's provider bills you for the tokens it uses, priced per million tokens of input and output. The xAI backend performs that step itself with xAI's model, so there xAI bills those tokens in addition to the $5 per 1,000 posts. A search therefore costs retrieval plus one answer, on either backend. See [twitterapi.io pricing](https://twitterapi.io/pricing) and [xAI pricing](https://docs.x.ai/developers/pricing).

### Retries, rate limits and coverage

- Only **429 and 503** are retried automatically, matching the provider's guidance. Other statuses surface immediately rather than repeating a request the upstream may already have billed.
- `Retry-After` is honoured in both numeric and HTTP-date form, and never shortened: a zero delay falls back to `retryBaseDelayMs` rather than becoming a hot loop, and a delay past the 60-second cap fails with a message naming the requested wait instead of retrying early.
- An HTTP 200 whose body cannot be read is not retried, because the page may already be billed. The failure says so.
- The HTTP status is always reported, including when the body is not JSON, which is common for 429s. A depleted balance comes back as `payment required: Credits is not enough.Please recharge`, and 402 is never retried.
- Stopping at the page cap, on a repeating cursor or on a missing cursor marks the result truncated and adds a `## Notes` line, so a partial answer is never presented as complete coverage. A missing cursor is not truncation once `count` is filled, or when an empty page ends a thread. An empty result from a truncated retrieval says retrieval stopped early instead of claiming nothing matched.
- A synthesis that fails or is aborted is an error, not an empty answer.
- Media downloads are bounded to three attempts per allowed attachment and 60 seconds per search, so a topic full of dead media URLs cannot stall a call. Anything skipped is disclosed.

Verbatim post objects, replies, quotes, media details, views and bookmarks are out of scope — use [@pi-lab/grok-build](../grok-build) for those.
